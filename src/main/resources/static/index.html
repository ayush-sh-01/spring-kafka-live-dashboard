Interview Architecture & Conceptual Reference

1. Second-Level Cache (Ehcache 3) vs First-Level (L1)

L1 Cache: Default in Hibernate. Lives only within one Session / HTTP request.
L2 Cache: Lives across the entire JVM. In this project, Geolocation and UserAgent tables rarely change. By caching them in L2 memory with Ehcache, any request needing country or device details is resolved in 0ms directly from RAM without database roundtrips.

2. The Interview Problem: Stale Cache Invalidation in Query Cache

The Trap: Query Cache caches aggregate results (e.g., SELECT count(*) FROM activity_logs). If logs are batch-written externally or directly, the query cache doesn't notice and returns stale counts.
The Solution: We route all activity writes through Hibernate's persistence context. When Hibernate persists ActivityLog, it automatically touches the internal update-timestamps-region, instantly invalidating the stale query cache. Furthermore, we enforce strict 5-minute TTL in ehcache.xml as a safety boundary.

3. JPA Criteria API vs Hardcoded SQL

Instead of risky and messy string concatenations like "WHERE 1=1 " + (filter ? "AND ..." : ""), the JPA Criteria API dynamically builds type-safe SQL predicates programmatically in Java based on whichever filters the dashboard user selects.

4. Solving the N+1 Query Disaster with @NamedEntityGraph

Fetching 50 logs with lazy associations naively causes 1 query for logs + 50 for users + 50 for locations + 50 for user agents = 151 queries!
With @NamedEntityGraph(name = "ActivityLog.detailedReport"), Hibernate issues ONE single SQL JOIN query, bringing all dimensions back in a single database roundtrip.

5. Kafka Streaming & WebSocket Push

High-volume clicks hit our REST API and are immediately queued into Kafka (buffering traffic spikes). An asynchronous consumer persists them. A @Scheduled aggregator computes metrics every 3 seconds and broadcasts updates live to your browser over WebSocket STOMP.
